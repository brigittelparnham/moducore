# Architecture

## Vision

A platform of composable, modular applications. Each app (CMS, journal, etc.) can:
- Run as a standalone application
- Be composed into the CMS as the host shell
- Be embedded into external sites (Notion, other CMSes, any website) as web components
- Feed data into each other
- Connect to external APIs and surface that data in any app

---

## Principles

- **CMS is the host.** It is the top-level shell where secondary apps are managed and displayed.
- **Secondary apps are independent.** They are usable standalone and embeddable elsewhere.
- **Apps can feed each other.** A journal can display hospitality order data. A CMS page can pull from a journal. No silos.
- **Tenants own their setup.** Multi-tenant from day one. Each tenant chooses which apps they install.
- **No vendor lock-in.** Everything is self-hosted and self-owned.

## Monorepo Structure

```
/
├── apps/
│   ├── api/           ← Hono API server (auth, tenancy, all business logic)
│   ├── cms/           ← CMS host app — installs/displays secondary apps
│   ├── journal/       ← Standalone journal app
│   └── web/           ← Marketing site (future)
├── packages/
│   ├── ui/            ← Shared component library (React)
│   ├── core/          ← Shared types, Zod schemas, constants
│   ├── db/            ← Drizzle schema, migrations, query helpers
│   ├── integrations/  ← External API connector system
│   └── embeds/        ← Web component wrappers for external embedding
├── docs/              ← Architecture, schema, roadmap
├── turbo.json
└── pnpm-workspace.yaml
```

## Tech Stack

| Layer | Choice | Reason |
|---|---|---|
| Frontend | React + Vite | Specified requirement |
| Monorepo | Turborepo + pnpm workspaces | Best DX at this scale |
| API server | Hono | Modern, TypeScript-first, runs anywhere |
| Database | PostgreSQL | Multi-tenant relational data |
| ORM | Drizzle | Stays close to SQL, excellent TS types, simple migrations |
| Auth | better-auth | Auth library (not a service) — you own everything |
| Embeds | Web Components | Most portable — works in Notion, any HTML context |
| Validation | Zod | Shared between frontend and backend via packages/core |

## App Composition Model

Secondary apps are **packages first, apps second**.

- `packages/journal` contains all journal logic and components
- `apps/journal` is a thin standalone wrapper around `packages/journal`
- `apps/cms` imports from `packages/journal` directly — no iframes, no indirection

This means:
- The CMS renders secondary app components natively with shared state and auth
- Secondary apps are independently runnable for development and standalone use
- Web component embeds in `packages/embeds` wrap the same package components

```
packages/journal  ──→  apps/journal    (standalone)
      │
      └──────────────→  apps/cms       (hosted inside CMS)
      │
      └──────────────→  packages/embeds → <journal-widget> (external embed)
```

## External Embedding (Web Components)

Each app exports one or more embeddable widgets as custom HTML elements.

Usage on any external site:
```html
<script src="https://yourplatform.com/embeds/journal.js"></script>
<journal-widget tenant="abc123" mode="read-write"></journal-widget>
```

- `tenant` — embed token that identifies the tenant and scopes permissions
- `mode` — `read-only` (default for public sites) or `read-write` (for owner's own sites)
- Tokens are generated by the API, stored in the DB, revocable

Web components wrap React components using `@r2wc/react-to-web-component`.

## Integration / Connector System

Any app can connect to external APIs (hospitality ordering, RSS, Shopify, etc.) and display that data.

- Connectors are configured per-tenant in the CMS settings
- Each connector has a type (e.g. `hospitality`, `rss`), credentials stored encrypted, and a fetch schedule
- Fetched data is cached in the DB and available to any app via a shared hook

```ts
// In any app component
const { data } = useConnector('hospitality', { query: 'todays-orders' })
```

```
packages/integrations/
  connectors/
    hospitality.ts   ← adapter: knows how to fetch + transform the API
    rss.ts
    shopify.ts
  runtime/
    fetcher.ts       ← unified fetch interface
    transformer.ts   ← maps external schema → internal schema
  ui/
    ConnectorConfig.tsx  ← lives in CMS settings panel
```

New connectors are added by creating a new adapter file. The runtime handles scheduling, caching, and error handling uniformly.

## Multi-Tenancy

- Every data table has a `tenant_id` column
- API middleware resolves tenant from the request (subdomain or session) and attaches to request context
- Every query is scoped to `tenant_id` — enforced at the query helper layer in `packages/db`
- Tenants select which apps to install — stored in `tenant_apps` table

Tenant resolution order:
1. Subdomain: `acme.yourplatform.com` → resolves tenant `acme`
2. Auth session: tenant embedded in session claims
3. Embed token: token carries `tenant_id`

---

## Auth Model

Handled by `better-auth` running inside `apps/api`. No external auth service.

- Email + password login
- Session-based (httpOnly cookies)
- Roles per tenant: `owner`, `admin`, `member`
- Embed tokens: separate token type, scoped to tenant + app + permissions

---

## Data Flow Summary

```
External API
    ↓
packages/integrations (connector fetches + caches)
    ↓
packages/db (stored in connector_data_cache)
    ↓
apps/api (served via API endpoint)
    ↓
apps/cms or apps/journal or packages/embeds (displayed in any app)
```
